    01

    Read almost everything.

    Pretraining starts as a stream of documents. Somewhere in it is a page that says “…the Eiffel Tower is in Paris.” Its “ Paris” is our token.

    1.1Pool the sources

    Crawled web pages, code, books, papers, math and many languages are pooled into one stream. Anthropic’s recent system cards describe the mix as public web data, licensed data, data from users who opted in, and data generated internally. They don’t publish proportions or totals.

    1.2Remove duplicates

    One common approach uses MinHash signatures to find and remove near-duplicate documents. Deduplication reduces repeated exposure, memorized output and wasted compute; it does not eliminate memorization. Claude’s exact deduplication pipeline is not published.

    02

    Cut into tokens.

    The text model receives token IDs. The byte-level BPE example here cuts text into pieces from a fixed vocabulary, and each piece becomes an integer ID.

    2.1Byte-pair encoding

    When training a byte-level BPE tokenizer, frequent adjacent byte sequences are merged to build a vocabulary. Encoding new text applies those learned merge rules. Common words can form one piece with a leading space; this example treats “ Paris” as one token. Its segmentation and ID are illustrative.

    Try it → Tokenizer

    ids = tokenizer.encode("is in Paris.")
# [382, 304, 12842, 13]   illustrative IDs

    03

    Predict the next one.

    Claude Fable 5.2 · Published API — 1M-token contextDeepSeek‑V4‑Pro · Representative internals — figures marked *

    Pretraining is one objective repeated trillions of times: given everything so far, put probability on the next token. The tower of layers you’ll meet again in stage 7 is built here.

    3.1Forward, in parallel

    A batch of sequences flows up the tower at once. A causal mask lets position n see only positions ≤ n, so every position in every sequence is its own prediction problem.

    Total parameters
    1.6T*

    3.2Score the guess

    After “…the Eiffel Tower is in”, the loss is the negative log of the probability given to “ Paris”. A multi-token-prediction head also predicts the token after that, which adds training signal at every position.

    loss = cross_entropy(logits[:, :-1], ids[:, 1:]) + λ · mtp_loss
    MTP depth
    1 extra token*

    3.3Update the weights

    Gradients flow back through the active computation, and the optimizer updates the model’s trainable weights. DeepSeek‑V4 uses Muon for most matrices and AdamW for embeddings, the output head and norms. Pretraining uses FP8 mixed precision; quantization-aware training (QAT) produces FP4 expert weights for the released model.

    04

    Learn what good looks like.

    Claude Fable 5.2 · Published API — no training recipeDeepSeek‑V4‑Pro · Representative internals — the recipe marked *

    A pretrained text model predicts continuations. Post-training turns the same tower into an assistant that follows instructions, uses tools and reasons toward answers it can check.

    4.1Imitate

    Supervised fine-tuning trains on curated demonstrations: conversations, tool calls, worked solutions. It uses the pretraining loss on much better data.

    4.2Try, grade, reinforce

    For a prompt with a checkable answer, the policy samples a group of attempts. Verifiers grade them: the tests pass, the final answer matches. Each score is compared with the group’s mean, so no separate value model is needed. Rewarding correct answers is also how a model learns to think before it answers.

    A_i = (r_i − mean(r)) / (std(r) + ε_std)
θ  ← θ + η · ∇ Σ_i A_i · log π_θ(attempt_i)
# ε_std > 0 avoids division by zero; equal rewards give A_i = 0
# simplified: GRPO also clips π_θ / π_old to 1 ± ε, PPO-style
    Method
    GRPO
    Shao et al., 2024
    Group of 8 in the drawing
    Illustrative

    05

    Pass the gate.

    Before a frontier model ships, it is tested for what it can do and for what it could be misused to do. After this gate the weights are frozen: everything training changed is now fixed, and no request will change it.

    5.1Evaluate

    Capability suites, agentic tasks and dangerous-capability evaluations (cyber, biology, autonomy) run on the final checkpoint. Anthropic publishes the results in a system card.

    06

    Your request arrives.

    Months later you ask “What’s the weather in Paris right now?” with a get_weather tool attached. The API is stateless: every call carries the whole conversation. What the call builds is temporary, activations and a KV cache that end with the request, apart from any prefix the prompt cache keeps for reuse, 5 minutes by default.

    07

    One pass up the tower.

    Claude Fable 5.2 · Published API — no internalsDeepSeek‑V4‑Pro · Representative internals — every figure, marked *

    This is the engine. The token’s vector rides a residual stream up 61 layers; each layer reads from the stream and writes back to it. Anthropic doesn’t publish Claude’s internals, so this stage uses DeepSeek‑V4‑Pro’s published design as a representative frontier architecture.

    7.1Look up a vector

    The ID selects one row of the embedding table: a lookup, not a multiplication. Out comes a vector of 7,168 numbers, the start of the residual stream.

    h = E[12842]        # float[7168]
    Hidden size
    7,168*
    DeepSeek‑V4‑Pro config
    Embedding table
    129,280 × 7,168*
    DeepSeek‑V4‑Pro config

    7.2Attend, sparsely

    RMSNorm rescales a copy of the vector, then causal attention uses only permitted current and earlier positions. In DeepSeek‑V4, compressed sparse attention (CSA) selects compressed entries with a lightweight indexer, while heavily compressed attention (HCA) reads more compressed summaries. Both also read a recent-token window. RoPE rotates part of each query and key to encode position.

    In plain words: each token looks back at earlier tokens to decide which ones matter. DeepSeek‑V4 keeps a compressed summary of the past, so it does not reread everything.

    Attention & KV mode, as drawn
    V4-Pro at 1M: ≈10% of V3.2’s stored KV. CSA selects compressed history; HCA reads heavily compressed summaries; both keep a recent window*

    Why it matters here: Each new token has to look back at the history. How much of it is read decides how much memory and bandwidth every step needs.

    Try it → Attention & KV

    blocks = topk(indexer(q, kv_compressed), k=1024)
out    = attend(q, kv_compressed[blocks] ∪ kv[-128:])

    7.3Route to 6 of 384 experts

    A router scores 384 expert networks and keeps the top 6, and one shared expert always runs. Their outputs are weighted and summed. That’s why only 49B of the 1.6T parameters touch this token.

    In plain words: this layer is a mixture of experts (MoE): it holds hundreds of small specialists, and a router picks six of them for this token while the rest stay idle.

    Try it → MoE router

    out = shared(x) + Σ_{j ∈ selected} g_j · expert_j(x)
g_j = 2.5 · s_j / Σ_{k ∈ selected} s_k
# s_j = sqrt(softplus(router_j(x))); load-balance bias selects experts only

    7.4Add back, sixty-one times

    Each sub-block’s output is added back to the stream, and the layer repeats 61 times with different weights each time: a stack, not a loop. The drawing keeps one stream for clarity; DeepSeek‑V4 widens it into four parallel streams mixed by learned doubly-stochastic matrices (manifold-constrained hyper-connections)*.

    In plain words: each layer adds its result to a running total instead of replacing it, so earlier information survives. Four parallel totals are blended with weights whose rows and columns each add up to 1, which keeps the numbers stable.

    Try it → 4-stream residual

    for layer in layers:
    h = h + layer.attn(rmsnorm(h))
    h = h + layer.moe(rmsnorm(h))
    Layers
    61*
    DeepSeek‑V4‑Pro config

    7.5Score the vocabulary

    Before the output head, the four hyper-connection streams merge through a learned reduction back to one 7,168-dimensional vector*. A final RMSNorm (preserving shape) and the LM head turn that vector into 129,280 logits, one per token, and softmax makes them probabilities. In the representative design, a small multi-token-prediction head sharing the output head also drafts the token after next, which serving can use to speculate*.

    In plain words: the model gives every word in its vocabulary a score, then turns the scores into probabilities.

    h = merge_4_to_1(streams)           # 4 × 7,168 → 7,168*
p = softmax(W_out · rmsnorm(h))     # 129,280 probabilities

    “ right” 0.31

    08

    Read the prompt in parallel.

    Serving runs the frozen tower in two phases. Prefill processes prompt positions in parallel, often in chunks, while layers remain sequential.

    8.1Parallel, often compute-bound

    Prefill computes prompt representations without learning or backpropagation. Parallel matrix operations often keep accelerators busy. Prompt length, reused cache state, scheduling and any generated reasoning all affect time to the first visible answer token.

    In plain words: prefill reads the whole prompt at once. Decode, which comes next, writes the reply one token at a time.

    Try it → Prefill vs decode

    8.2Fill the KV cache

    Each layer caches attention state to avoid repeating earlier computation. DeepSeek‑V4 combines compressed entries with a recent-token window; its cache does not retain one permanent entry per token. It stores the positional dimensions in BF16 and the rest in FP8.

    In plain words: the cache is the model’s notes on everything it has read, so it does not reread the prompt for each new token.

    Attention & KV mode, as drawn
    V4-Pro at 1M: ≈10% of V3.2’s stored KV. CSA selects compressed history; HCA reads heavily compressed summaries; both keep a recent window*

    Why it matters here: Prefill just built this cache. Its size decides how many requests fit in GPU memory and how fast each decode step can read it.

    KV storage
    FP8 + BF16 RoPE dims*
    DeepSeek‑V4 paper

    8.3Batched with strangers

    In the common serving design illustrated here, a scheduler re-forms batches at each iteration, admitting work as memory and compute allow. Finished requests can leave independently. Continuous batching and paged KV storage are published techniques; Claude’s scheduler and cache layout are not published.

    09

    Think before answering.

    On Fable 5.2, adaptive thinking is always enabled. The model decides whether and how much reasoning a turn needs. When it reasons, reasoning tokens are generated through the decode loop before or between other output.

    9.1Effort sets the depth

    You don’t set a separate thinking-token budget. You set effort, from low to max, and the model decides whether and how much to think. Effort also affects answer and tool-call tokens. For Fable 5.2, Anthropic suggests starting at high.

    Effort, as drawn
    16 thinking tokens in the drawing (illustrative; actual use varies by request)
    Effort levels
    low → max
    Anthropic docs

    9.2Readable reasoning is summarized

    Raw reasoning is never returned as readable text. Thinking blocks include an encrypted signature and, by default, an empty readable field (display: "omitted"); "summarized" returns a summary. Pass complete thinking blocks back unchanged during tool loops. Thinking is billed the same in either display mode.

    thinking: { type: "adaptive", display: "summarized" }

    9.3Reasoning picks the tool

    Here the model works out that it can’t know today’s weather and should call get_weather. Every reasoning step attends over the KV cache, “ Paris” included.

    10

    One token per step.

    After prefill, basic autoregressive generation repeats a forward pass for each next token. Attention reads the cached history selected by its mechanism; sparse attention does not read every stored entry.

    10.1Memory-bound

    Basic decode often spends much of its time reading active weights and selected cached history from memory. The bottleneck depends on hardware, batch size and context length. Decode speed is measured in tokens per second; sparse experts and compressed caches can reduce the work.

    10.2Sample

    The model produces a probability distribution over possible next tokens. Sampling selects one token from that distribution, which becomes the next step in the generated reasoning, tool call or answer. The exact sampling policy for Fable 5.2 is controlled by the model provider.

    10.3Draft, then verify

    A cheap draft proposes the next token or two, and the next pass of the big model checks them in parallel. In the representative design the draft comes from the MTP head*. When a draft is accepted, one target pass verifies two tokens; the net speedup depends on draft cost and acceptance rate. Anthropic doesn’t publish how Claude is served.

    Technique
    Speculative decoding
    Leviathan et al., 2023

    Token IDs are decoded back into text and sent to your app as server-sent events while generation is still running.

    Token pieces are decoded into text, and SSE carries UTF-8 data. Token and network chunk boundaries can split a character’s bytes; a streaming UTF-8 decoder buffers incomplete sequences before presenting text.

    12

    Call a tool. Continue.

    The model can’t check the weather itself. It stops, your code does the work, and the conversation goes back in.

    12.1Your code runs the tool

    Claude doesn’t execute get_weather; your app does. Keep the complete assistant response unchanged, including thinking signatures, then append a tool_result. Treat that result as untrusted input. Server tools such as web search and code execution run on Anthropic’s side instead.

    { "type": "tool_result", "tool_use_id": "toolu_…",
  "content": "{\"temp_c\": 18, \"conditions\": \"clear\"}" }   # illustrative

    12.2A new request, a warm prefix

    In this Messages API example, the app resends the conversation, including the complete assistant response and the tool result. If caching is enabled and an eligible matching prefix is still available, that prefix is reused. New assistant and tool-result content belongs to the uncached suffix unless it was already cached.

    Why it matters here: Every tool round trip resends the whole conversation. A warm prefix keeps each repeat cheap and fast instead of recomputing everything.

    Glossary
    Token
    A piece of text, such as a word, part of a word or punctuation, that the model reads and writes as one integer ID.
    KV cache
    The stored keys and values for earlier tokens, kept so attention does not recompute them for every new token.
    Prefill
    The first serving phase: the whole prompt is processed in parallel and the KV cache is filled.
    Decode
    The second serving phase: the reply is generated one token at a time, each step reading the cache.
    Logits
    The raw score the model gives every vocabulary entry before softmax turns the scores into probabilities.
    MoE
    Mixture of experts: a router sends each token to a few specialist sub-networks instead of running the whole layer.
    SSE
    Server-sent events: a one-way stream of text from server to browser over ordinary HTTP.
    CSA
    Compressed sparse attention: a token reads a small, selected set of compressed history entries.
    HCA
    Heavily compressed attention: the history squeezed far harder into summaries, trading detail for memory.
    RMSNorm
    A step that rescales a vector so its average size stays steady before the next layer.
    RoPE
    Rotary position embedding: it encodes where a token sits by rotating its query and key vectors.
    Doubly-stochastic matrix
    A grid of non-negative numbers whose rows and columns each add up to 1, so mixing with it neither grows nor shrinks the total.
    Manifold-constrained hyper-connections (mHC)
    Several parallel residual streams mixed by learned matrices that are constrained to stay stable.
