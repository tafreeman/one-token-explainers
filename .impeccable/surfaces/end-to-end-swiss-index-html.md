# Swiss token instrument

## Scope and visitor mode

Target: `end-to-end-swiss/index.html`, the default site entry. Visitor mode:
**Experience**, explicitly requested by the user. Extend the incumbent Swiss
world: paper, precise black geometry, orange reserved for the token, existing
lettering. Preserve the single interface and optional depths.

## Confirmed direction

The user chose **Token instrument**: make the existing 3D journey dominant;
scrubbing moves Paris through its forms, detail opens with spatial continuity,
and the finale lands it in the reply. Code-first. Reuse the existing renderer.

## First viewport and action

A compact title/action area sits above the large existing 3D line. The token's
changing form sits beside the title. The diagram owns most of the available
viewport; optional playback, readout and introductory context sit below it.
Explore starts the instrument without scrolling; the axis and previous/next
controls operate it. Reading remains one visible secondary action.

## Delight thesis

Curiosity should feel like handling the same token as it changes form, ending
with the familiar word in the illustrative reply; avoid unrelated celebration.

## Motion thesis

- **Focal moment:** the orange token travels through the existing geometry as a
  user-controlled instrument, then resolves into the reply's word.
- **Continuity:** the existing scene stays beside the learner while an inline
  detail sheet reveals from its own summary. Reversals and repeated actions must
  remain responsive.
- **Feedback:** direct range feedback, bounded camera settling, clear step
  controls and a short arrival treatment. No unsolicited audio.
- **Budget:** no new renderer, library or nonessential idle loop. Reuse the two
  existing views; suspend work when hidden/offscreen. Reduced motion replaces
  spatial travel and clipping with immediate state and restrained color feedback.

## Constraints and verification

Retain all lesson facts, sources, native keyboard semantics, captions, local-file
operation and text when WebGL fails. Desktop and phone checks, normal/reduced
motion captures, a fresh shipped motion reviewer, and the existing repository
gates form the verification. Real-device smoothness remains unverified unless
measured on that device. Other presentations are secondary and keep their URLs.
